## 重要度: 高

### 1. 拡張子だけ違う画像が最適化後に衝突し、別の画像に差し替わる（バグ・再現済み）

**場所**: `scripts/images.py:160`（`out_rel = str(Path(rel).with_suffix(ext).as_posix())`）

TIFF・BMP・WebP・GIF は PNG / JPEG に変換され、出力ファイル名は拡張子だけが変わります。そのため `images/diagram.tiff` と `images/diagram.png` が両方あると、最適化版はどちらも `images/diagram.png` になり、後から処理した画像で上書きされます。

再現手順: 赤い `diagram.png` と青い `diagram.tiff` を別々の図として参照してビルドすると、`manifest.json` の対応表は両方とも `images/diagram.png` になり、EPUB には青い画像 1 枚しか入りませんでした（**赤い図が消え、両方の図が青い画像になる**）。エラーも警告も出ません。`photo.jpg` と `photo.webp`（→ JPEG）のような組み合わせでも同じことが起きます。

**修正の提案**
- 拡張子が変わるときは元の拡張子を名前に残す（`diagram.tiff` → `diagram.tiff.png`）か、パスのハッシュを付ける
- あわせて、出力パスが重複したら `ValueError` で止める安全策を入れる（`new_entries` の `output` が重複しないか確認する）

### 2. 辞書の誤検出で `npm run lint:fix` が原稿を壊す（バグ・再現済み）

**場所**: `lint/dict/technical.yml:89-95`（`様に` → `ように`）、`:48-52`（`少([いくかけ])`）

`/(?<![同異多仕模王皆])様に/` は「お客様に」「神様に」「奥様に」「先生様に」なども誤りとして検出し、自動修正できるエラーとして報告します。テスト用の原稿に「お客様にお届けします。」と書くと `✖ 様に => ように (自動修正可) [prh]` になり、`lint:fix` を実行すると **「お客ようにお届けします。」に書き換わります**。エラーなので CI も失敗します。ビジネス書・実用書ではよく使う表現です。

同じように、`少([いくかけ])` は「減少か」「多少か」にも当てはまり、「減少なか」と直してしまうおそれがあります。

**修正の提案**
- `様に` は「の様に」「この様に」「その様に」「どの様に」など、直前が「の」や指示語のときだけに絞る（例: `/(?<=[のこそあど])様に/`）か、敬称を除く（`(?<![客神奥皆王]|先生|社長)` などを加える）
- `少([いくかけ])` には `(?<![減多希僅])` を付ける
- 誤検出を確かめる `specs`（`from: お客様に` → `to: お客様に`）を辞書に足す
- 自動修正の影響が大きいルールは `prh` から外し、警告として扱うことも検討する

### 3. `scripts/setup.sh` が最近の Linux / macOS で途中で止まる（使いにくさ）

**場所**: `scripts/setup.sh:57-60`、`:23-24`

- `python3 -m pip install --user ... || python3 -m pip install ...` は、PEP 668（externally-managed-environment）を採用している Ubuntu 23.04 以降（**WSL の既定の Ubuntu 24.04 を含む**）・Debian 12・Homebrew の Python では、どちらのコマンドも失敗します。`set -e` なので、その後の EPUBCheck・npm のインストールに進まずに終わります。Ubuntu は `python3-pip` が最初から入っていないことも多いです
- pandoc がすでにあれば、バージョンを見ずに「導入済み」と表示します。Ubuntu 22.04 の apt の pandoc は 2.9 なので、セットアップは成功したように見えて、`make` で「pandoc 3.1 以上が必要です」と失敗します

**修正の提案**
- リポジトリ直下に `.venv` を作ってその中にインストールし、Makefile の `PYTHON ?=` で `.venv/bin/python` があれば優先する。または `pipx` / `--break-system-packages` の案内を出す
- pandoc が見つかったら `pandoc --version` を `MIN_PANDOC`（3.1）と比べ、古ければ .deb を入れ直すか警告する
- `curl` / `unzip` が無い場合のメッセージを出す
- README の「セットアップ」と「トラブルシューティング」に `externally-managed-environment` の対処を書く

### 4. Node.js の必要なバージョンが実際と合っていない（ドキュメント / バグ）

**場所**: `package.json:78-80`（`"node": ">=20"`）、`README.md:104-105, 119, 398, 694`、`docs/tutorial.md:57, 115`、`scripts/check-manuscript.mjs:584`

- インストールされる `@vivliostyle/cli` 11.4.0 の `engines` は `"node": ">=22.12.0"` です（`node_modules/@vivliostyle/cli/package.json` で確認）。Node 20 では `make paperback` が動かないか、動作が保証されません。textlint 15.8 も `>=20.18.0` で、単なる「20 以上」ではありません
- Node.js 20 は 2026 年 4 月でサポートが終わっています
- `check-manuscript.mjs` は `NODE_USE_ENV_PROXY` でプロキシを使わせていますが、この環境変数があるのは比較的新しい Node（v24、v22 の後期版）だけです。README の「`HTTPS_PROXY` を設定する（自動でプロキシを使う）」は、古い Node では効きません

**修正の提案**
- `engines` を `">=22.12"` にし、README・チュートリアルの「Node.js 20 以上」を「22.12 以上（推奨 24 LTS）」に直す
- `.nvmrc` か `package.json` の `volta` でバージョンを固定する。CI（`node-version: "22"`）と揃える
- `NODE_USE_ENV_PROXY` が使えない Node では、プロキシが効かないことを警告する

### 5. EPUB に HTML の表紙ページが入っている（KDP）

**場所**: `scripts/build.py:176-185`（`cover-image` を pandoc に渡す）、`:393-424`（後処理）、`README.md:958`

pandoc は `cover-image` を渡すと `text/cover.xhtml` を作り、spine の先頭に `linear` の項目（`<itemref idref="cover_xhtml" />`）として入れます（サンプルの EPUB で確認）。Kindle Publishing Guidelines には「表紙画像に加えて HTML の表紙ページを本文に入れないこと。表紙が 2 回表示されたり、変換に失敗したりすることがある」という記述があります（検索で見つかった KDP ヘルプの記述）。また、KDP では電子書籍の表紙を EPUB とは別にアップロードするので、本文の中に表紙ページは要りません。

README の「表紙画像は EPUB にも埋め込む（`cover-image`）」という設計上の判断自体はよいのですが、表紙を **画像としてだけ** 持つ（manifest の `properties="cover-image"`）のか、**本文のページとしても** 持つのかが分けて考えられていません。

**修正の提案**
- `postprocess()` で spine の `cover_xhtml` を `linear="no"` にする（または spine から外して manifest からも消す）。`cover-image` の画像そのものは残す
- `book.yaml` に `layout.cover_page: false`（既定）のような設定を用意し、Apple Books など向けに残したい人だけ有効にする
- README の「Kindle Previewer で確認が必要な点」に「表紙が 2 回出ていないか」を足す
- 公式の記述をアップロード前に [電子書籍の表紙の作成（KDP ヘルプ）](https://kdp.amazon.com/help/topic/G6GTK3T3NUHKLEFX) と Kindle Publishing Guidelines で確認する

### 6. JPEG の EXIF（GPS 位置情報など）がそのまま EPUB に入る（バグ・個人情報・再現済み）

**場所**: `scripts/images.py:295-303`、`README.md:643`

README の表には「EXIF の回転情報 → 回転を反映してからメタデータを削除」とありますが、実際にメタデータが消えるのは **再エンコードしたとき** だけです。回転情報が無く、サイズの上限内に収まっている JPEG は「変更なし」としてそのままコピーされます（`data is None` → `shutil.copyfile`）。

再現手順: GPS 情報（`0x8825`）と機種名を埋め込んだ 800×600 の JPEG を原稿に入れてビルドすると、EPUB 内の `media/file1.jpg` に GPS 情報と機種名が残っていました。スマートフォンで撮った写真では、**撮影場所（自宅など）を読者に配布する**ことになります。

**修正の提案**
- JPEG は再圧縮せずに、APP1（EXIF / XMP）・APP13（IPTC）などのマーカーだけを取り除く処理を入れる（Python でセグメントを読み飛ばすだけで実装できる。ICC プロファイルの APP2 は残す）
- 最適化を無効にしたとき（`--no-optimize-images`）や Pillow が無いときは、元画像に EXIF の GPS 情報があれば警告する
- README の記述を実際の動作に合わせる
- `OPTIMIZER_VERSION` を上げて、キャッシュ済みの画像も作り直させる

### 7. アクセシビリティのメタデータが無い（KDP / EAA）

**場所**: `scripts/build.py:393-424`（OPF の後処理）、README の「設計上の判断」

欧州アクセシビリティ法（EAA）が 2025 年 6 月 28 日に施行され、EU の消費者に販売する電子書籍には、アクセシビリティへの対応とその情報（EPUB Accessibility 1.1 の `schema:accessMode`・`schema:accessibilityFeature`・`schema:accessibilityHazard`・`schema:accessibilitySummary`、`dcterms:conformsTo` など）が求められるようになりました。Amazon もアクセシビリティのメタデータを取り込むと報じられています（[参考](https://www.fondazionelia.org/en/whats-new/amazon-kindle-will-ingest-accessibility-metadata-following-the-onix-3-1-standards/)、[W3C: EPUB Accessibility – EU Accessibility Act Mapping](https://www.w3.org/TR/2022/NOTE-epub-a11y-eaa-mapping-20220415/)）。KDP のデフォルトの出版地域は「すべての地域」なので、日本語の本でも EU のストアで販売されます。

このテンプレートの EPUB には、アクセシビリティのメタデータが 1 つも入っていません。キャプションの無い画像（`![](images/x.png)`）は代替テキストが空になることもあります。

**修正の提案**
- `postprocess()` で OPF に次のような既定値を入れる（`book.yaml` の `accessibility:` で上書きできるようにする）
  - `schema:accessMode` = `textual`（画像があれば `visual` も）、`schema:accessModeSufficient` = `textual`
  - `schema:accessibilityFeature` = `structuralNavigation`, `tableOfContents`, `readingOrder`, `alternativeText`（画像に説明があるとき）, `rubyAnnotations`（ルビがあるとき）
  - `schema:accessibilityHazard` = `none`、`schema:accessibilitySummary`
- `npm run lint` に「代替テキストの無い画像」の警告を加える
- EPUBCheck の Ace（DAISY）での確認を CI に入れることを検討する
- KDP 側でどの情報が使われるかは、KDP ヘルプで最新の内容を確認する（要確認）

## 重要度: 中

### 8. CI の Summary に EPUBCheck の表が出ない（バグ / ドキュメント）

**場所**: `scripts/build.py:438-449`、`scripts/validate.py:137-146`、`README.md:924`

README には「各ジョブの『Summary』に EPUB ごとの件数の表が出ます」とありますが、表を書き出す `write_github_summary()` は `validate.py` の `main()` からしか呼ばれません。CI は `build.py --check` で検証していて、その中では `validate.validate()` だけを呼ぶので、表は出ません。

**修正の提案**: `build.py` の `main()` で検証結果を集め、最後に `validate.write_github_summary(rows)` を呼ぶ（`run_epubcheck()` から `(epub, ok, counts)` を返す）。

### 9. ペーパーバックで日本語フォントが無いと、別の言語のフォントに黙って置き換わる（バグ・再現済み）

**場所**: `scripts/paperback.py:81-88, 507-527`

日本語フォント（Noto CJK など）が無い環境でビルドすると、Chromium が `WenQuanYi Zen Hei`（中国語のフォント）などに置き換え、PDF は警告なしで作られます。今回の環境では埋め込みフォントが `IPAGothic, WenQuanYiZenHei, LiberationSerif, ...` になりました。中国語のフォントでは、漢字の字形が日本語と違うものがあります。そのまま入稿すると、紙の本で初めて気付くことになります。

**修正の提案**: `inspect_pdf()` で取り出したフォント名と `FONT_STACKS` の和文フォントを照合し、本文の書体（`paperback.font`）が使われていなければ警告（CI ではエラー）にする。

### 10. ペーパーバックの奥付の罫線が KDP の最小の線幅より細い（KDP）

**場所**: `styles/print.css:130, 141`（`0.5pt solid black`）

KDP のペーパーバックのガイドラインでは、線は 0.75pt（0.01 インチ、0.3mm）以上の太さにすることになっています（[KDP ヘルプ](https://kdp.amazon.com/help/topic/G202145060)）。奥付の 2 本の罫線は 0.5pt です。表・囲み・コードの枠は `1px`（= 0.75pt）でちょうど下限なので、`book.yaml` の `css` で細くすると下回ります。

**修正の提案**: `print.css` の罫線を `0.75pt` 以上にする。README の「KDP の要件に合わせていること」の表に線幅を加える。

### 11. PDF のフォント埋め込みチェックが甘い（バグ）

**場所**: `scripts/paperback.py:326-330`

`unembedded = (フォントの数) and embedded == 0` なので、フォントが 1 つでも埋め込まれていれば、残りが埋め込まれていなくても合格になります。KDP はすべてのフォントの埋め込みを求めています。

**修正の提案**: フォントの辞書（`/FontDescriptor`）ごとに `/FontFile*` があるか数え、無いもの（Type3 は除く）を名前付きで報告する。`pypdf` などのライブラリを任意で使えるようにすると、ページ数（`/Pages` の `/Count`）の取得も確実になる。

### 12. `--writing-mode` で縦書き版と横書き版が同じファイル名になる（バグ）

**場所**: `scripts/build.py:247-249, 344-346`

`book.yaml` に `output:`（または `paperback.output:`）を書くと、`--writing-mode` を付けても名前に `-vertical` / `-horizontal` が付きません。`make check-modes` / `make paperback-modes` と CI の `dist/modes` では 2 回目のビルドで上書きされ、成果物には片方しか残りません。表紙（`<名前>-cover.jpg`）も同じです。

**修正の提案**: `--writing-mode` があるときは、`output` の値の拡張子の前に `-{mode}` を付ける（`my-book.epub` → `my-book-vertical.epub`）。

### 13. 画像を再エンコードすると ICC プロファイルが消える（バグ）

**場所**: `scripts/images.py:339-348`（`encode()`）

縮小・透過の除去などで再エンコードするとき、`icc_profile` を渡していないので、ICC プロファイルが消えます。iPhone の写真（Display P3）や Adobe RGB の画像は、sRGB として解釈されて色が変わります。

**修正の提案**: `ImageCms` で sRGB に変換してから保存する（変換できないときは元の `im.info["icc_profile"]` を引き継ぐ）。CMYK → RGB の変換も、プロファイルを使って行う。

### 14. 同じファイルの中の ID の重複を lint が検出しない（バグ）

**場所**: `scripts/check-manuscript.mjs:332-337`

重複の判定が `explicitIds.get(id) !== file` なので、同じファイルの中で `{#sec:a}` を 2 回使っても報告されません（テストで確認）。ビルドでも pandoc の `[WARNING] Duplicate identifier` が出るだけで成功し、相互参照は後の方の定義を指します。

**修正の提案**: 同じファイルの中の重複もエラーにする（2 回目の位置を報告する）。`build.py` でも pandoc の `Duplicate identifier` の警告を拾って、ビルドの警告一覧に出す。

### 15. ライセンスが無い・README からチュートリアルへのリンクが無い（ドキュメント）

- リポジトリに `LICENSE` が無く、テンプレートとして使ってよい範囲（改変・商用出版・サンプル画像の扱い）が分かりません。チュートリアルは「Use this template」を勧めているので、まず確認されるところです
- `docs/tutorial.md` が README から一度もリンクされていません。README の「ディレクトリ構成」にも `docs/` がありません（`README.md:47-91`）

**修正の提案**: `LICENSE` を追加し（コードは MIT など、サンプル原稿・画像は CC0 など）、README の冒頭と目次に「はじめての方は [チュートリアル](docs/tutorial.md)」を加える。ディレクトリ構成に `docs/tutorial.md` と `docs/review-2026-11.md` を足す。

### 16. チュートリアルでは Java が「推奨」なのに、`make check` は Java が無いと失敗する（ドキュメント）

**場所**: `docs/tutorial.md:56, 105, 123-127`

手順 1 では「Java 11 以上 + EPUBCheck: 推奨」ですが、手順 3-3 の動作確認は `make check` で、Java が無いと必ず失敗します。初めての人は「準備に失敗した」と受け取ります。

**修正の提案**: 手順 3-3 を「まず `make` でビルドできるか確認 → Java を入れたら `make check`」の 2 段階にする。または Java を「必須」にする。

### 17. 淡い色の表紙に枠が付かない（KDP）

**場所**: `scripts/cover.py:741-744, 819, 857-860`

KDP ヘルプでは、白や淡い色の背景の表紙は白い画面に溶け込むので、**中間色のグレーの細い枠（3〜4px）** を付けるよう勧めています（[KDP ヘルプ「電子書籍の表紙の作成」](https://kdp.amazon.com/help/topic/G6GTK3T3NUHKLEFX)。検索結果の記述）。縦書きのデザインの既定の背景は生成り色（`#f7f2e8`）です。飾り罫を描く既定の設定（`decoration: true`）では枠がありますが、`decoration: false` や淡い `colors` を指定すると枠の無い表紙になります。

**修正の提案**: 背景の端の明るさが一定以上のときは、`decoration` の設定に関係なく、外周に `#808080` の 3〜4px の枠を描く（`cover_design.border: auto / true / false`）。

### 18. 縦書きの `sideways` 表示の「端末を右に傾けると読める」の向き（ドキュメント・要確認）

**場所**: `README.md:837`、`books/vertical-sample/chapters/02-first-script.md:17-18`

`text-orientation: sideways` では文字が時計回りに 90° 回るので、横書きとして読むには端末を **反時計回り（左回り）** に回す必要があります。「右に傾ける」は、一般には時計回りと受け取られます。

**修正の提案**: Kindle Previewer の実際の表示で確認し、「端末を左に 90° 回す（右側を上にする）」のように回す向きが分かる書き方にする。

### 22. lint の TIFF の警告がビルドの動作と合っていない（使いにくさ）

### 23. 表紙・ISBN のチェックの抜け（KDP / 使いにくさ）

### 24. CI の小さな改善点（CI）

**場所**: `.github/workflows/build.yml`、`.github/workflows/lint.yml`

- ペーパーバックのジョブも `setup-tools` で Java と EPUBCheck を入れています。使わないので時間の無駄です（`setup-tools` に `epubcheck: false` の入力を足す）

- Python は 3.12 だけで試しています。README は「3.9 以上」なので、3.9 もマトリクスに入れるか、最低バージョンを上げる

### 27. `-epub-text-orientation` の値（KDP・要確認）

**場所**: `styles/vertical.css:235-237, 274-289, 307-311`

EPUB 3.0.1 で定められた接頭辞付きの `-epub-text-orientation` の値は、古い CSS の草案に合わせた `vertical-right`（現在の `mixed`）と `sideways-right`（現在の `sideways`）です。`-epub-text-orientation: mixed` / `sideways` を正しく解釈しないリーダーがあるかもしれません。EPUBCheck は CSS の値までは確かめないので、0 件でも気付けません。

**修正の提案**: Kindle Previewer と主要なリーダーで縦書きの英字・コードの向きを確認し、必要なら `-epub-text-orientation: vertical-right` / `sideways-right` を併記する。
