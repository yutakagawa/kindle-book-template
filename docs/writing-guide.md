## 1. 書きはじめる前に

本文を書く前に、次の 3 つを 1 行ずつ書き出しておくと、章立てや説明の深さで迷いにくくなります。

| 決めること | 例 |
|:--|:--|
| 読者は誰か | 「Python を少し触ったことがある事務職の人」 |
| 読み終えたら何ができるか | 「毎日の集計作業をスクリプトで自動化できる」 |
| 扱わないこと | 「Web アプリ開発、クラスの設計」 |

「扱わないこと」を決めておくと、説明が横道にそれにくくなります。
迷ったときは「この段落がなくても、読者は目標にたどり着けるか」を考え、たどり着けるなら削るかコラム（[7 章](#7-囲み脚注ルビの使い分け)）に回します。

### 横書きか縦書きか

技術書は、コードや英数字が多いため **横書き** が基本です。
コードが少なく文章が中心の実用書・入門書なら、**縦書き** も選べます。
どちらにするかは `book.yaml` の 1 行で切り替えられますが、縦書きでは書き方を工夫したほうがよい点があるので（[8 章](#8-縦書きで気をつける点)）、書きはじめる前に決めておきましょう。

```yaml
layout:
  writing_mode: horizontal   # horizontal = 横書き・左綴じ / vertical = 縦書き・右綴じ
```

## 2. 章立ての考え方

### 読者の作業の順に並べる

技術書の章は「技術の分類」ではなく「読者が手を動かす順」に並べると、読み進めやすくなります。

```text
✕ 分類の順          ○ 作業の順
  第1章 変数            第1章 はじめてのスクリプトを動かす
  第2章 制御構文        第2章 ファイルを一括でリネームする
  第3章 関数            第3章 Excel の集計を自動化する
  第4章 ファイル操作    第4章 毎日決まった時間に実行する
```

作業の順に並べると、変数や関数といった要素は「必要になった章」で少しずつ登場します。
読者は各章の終わりに「動くもの」を手に入れられるので、途中でやめにくくなります。

### 1 章の大きさの目安

Kindle では、読者は端末の下部に表示される「章の残り時間」を見ながら読み進めます。
**1 章は 15〜30 分で読める長さ（およそ 5,000〜12,000 字）** を目安にすると、通勤時間などの細切れの時間でも 1 章ずつ区切って読めます。
長くなった章は 2 つに分け、短すぎる章は前後の章とまとめましょう。

| 単位 | 記法 | 目安 |
|:--|:--|:--|
| 章 | `#` | 5,000〜12,000 字。1 ファイルに 1 つ |
| 節 | `##` | 1,500〜3,000 字。1 章に 3〜6 個 |
| 項 | `###` | 必要なときだけ。目次には既定では載らない |

見出しは `###`（項）までにとどめます。それより深くすると、小さな画面では階層の違いが見分けにくくなります。

### 1 ファイル = 1 章で書く

このテンプレートでは、章ごとに 1 つの Markdown ファイルを作り、`book.yaml` の `chapters` に並べます。
ファイル名に番号を付けておくと、並び順がひと目でわかります。

```yaml
chapters:
  - chapters/00-preface.md     # はじめに
  - chapters/01-first-run.md   # 第1章
  - chapters/02-rename.md      # 第2章
  - chapters/90-appendix.md    # 付録A
  - chapters/99-afterword.md   # おわりに
```

章の種類は、見出しの後ろの属性で指定します。

```markdown
# はじめに {.unnumbered}
# はじめてのスクリプトを動かす {#sec:first-run}
# よく使うコマンド一覧 {.appendix}
# おわりに {.unnumbered}
```

- `{.unnumbered}` … 番号なしの章（まえがき・あとがき）
- `{#sec:ID}` … 「第1章」のように番号が付き、`@sec:ID` で参照できる
- `{.appendix}` … 「付録A」のように番号が付く

### 「はじめに」に書くこと

Kindle ストアの「サンプルを送信」では、本の冒頭だけが読めます。
購入を決めるのは「はじめに」と第 1 章の書き出しであることが多いため、ここには次の内容を短く書きます。

- この本の対象読者と、読み終えたらできるようになること
- 必要な前提知識と環境（OS、ソフトのバージョン）
- 本書の読み方（どの章から読んでもよいか、サンプルコードの入手先など）

### 各章の書き出しと締めくくり

章の冒頭の 2〜3 行で「この章で何ができるようになるか」を伝え、章の終わりで「何ができたか」を振り返ります。
相互参照を使うと、前後の章へのつながりも示せます。

```markdown
# ファイルを一括でリネームする {#sec:rename}

この章では、フォルダの中の写真のファイル名を、撮影日の順に連番へ変えます。
@sec:first-run で作った実行環境をそのまま使います。

（本文）

## まとめ

- `Path.glob()` でファイルの一覧を取得できる
- ファイル名の変更は元に戻せないので、コピーで試す

次の @sec:excel では、同じ考え方で Excel の集計を自動化します。
```

## 3. Kindle で読みやすい文章の長さ

Kindle の画面は、スマートフォンでは紙の本より小さく、文字の大きさも読者が自由に変えます。
**1 画面に表示される文字数が少ない** ことを前提に、短く区切って書くのがコツです。

### 目安

| 単位 | 目安 | 理由 |
|:--|:--|:--|
| 1 文 | **60 字以内**（長くても 100 字） | 1 文が画面の 3 行を超えると、主語と述語の対応を見失いやすい |
| 読点 | 1 文に 3 つまで | 読点が多い文は、たいてい 2 文に分けられる |
| 1 段落 | **3〜5 文（200 字程度）** | スマートフォンで 1 画面に収まり、段落の区切りが見える |
| 箇条書き | 1 項目 1〜2 行、5〜7 項目まで | 項目が多いときは小見出しで分ける |

このテンプレートの原稿チェック（`npm run lint`）は、1 文が 100 字を超えたときや、読点が 4 つ以上あるときに警告を出します。

### 長い文を分ける

```text
✕ 本書で使うスクリプトはすべて GitHub で公開しているので、自分で入力するのが
  面倒な場合はダウンロードして使ってもかまいませんが、最初の数本は手で入力した
  ほうが、エラーの読み方が身につくのでおすすめです。（105 字）

○ 本書で使うスクリプトは、すべて GitHub で公開しています。
  ダウンロードして使ってもかまいません。
  ただし、最初の数本は手で入力するのがおすすめです。エラーの読み方が身につきます。
```

### 段落の区切りと改行

段落は空行で区切ります。原稿の中で改行しても、日本語の文の途中なら余計な空白は入りません。
**1 文ごとに改行して書く** と、差分が見やすく、原稿チェックの指摘も行で探しやすくなります。

```markdown
ファイル名の変更は元に戻せません。
はじめて試すときは、必ずフォルダのコピーで実行してください。

次に、実行結果を確かめます。
```

上の例は 2 つの段落になります（1 段落目の 2 行は 1 つの段落としてつながります）。

### そのほかのコツ

- **「です・ます」と「である」を混ぜない**。原稿チェックで混在を検出できます
- **指示語（これ、それ、上記）を減らす**。Kindle では前のページが見えないため、「上記の設定」より「`book.yaml` の `layout` の設定」と書くほうが確実です
- **「上の図」「次のページ」と書かない**。文字の大きさで配置が変わるため、図・表・リストは番号で参照します（[5 章](#5-図画像の入れ方)）
- **表記をそろえる**。「サーバ／サーバー」のような表記ゆれは原稿チェックで検出できます。本独自の表記ルールは `lint/dict/project.yml` に追加します

## 4. コードの入れ方

### 基本

コードブロックには必ず言語名を付けます。シンタックスハイライトされ、白黒の Kindle 端末でもキーワードが太字、コメントが斜体で区別できます。

````markdown
```python
def greet(name: str) -> str:
    # f文字列で埋め込む
    return f"こんにちは、{name}さん！"
```
````

ハイライトが不要なもの（実行結果、ディレクトリ構成など）には `text` を付けます。

````markdown
```text
001.jpg
002.jpg
```
````

### 番号付きのリストにして参照する

本文から参照するコードには、ID とキャプションを付けます。「リスト1.1」のような番号が付き、`@lst:ID` でリンクできます。

````markdown
[@lst:rename]は、写真のファイル名を連番にするスクリプトです。

```{.python #lst:rename caption="写真のファイル名を連番にする"}
from pathlib import Path

folder = Path("photos")
for i, path in enumerate(sorted(folder.glob("*.jpg")), start=1):
    path.rename(folder / f"{i:03d}.jpg")
```
````

### 1 行の長さは 60 文字まで

Kindle では横スクロールができません。長い行は自動で折り返されますが、折り返しの位置によってはコードの構造が読み取りにくくなります。
**1 行はおおむね 60 文字以内**（インデントを含む）に収めましょう。

```python
# ✕ 1 行が長い
result = [normalize(row["name"]) for row in load_rows("data.csv") if row["active"]]

# ○ 途中の結果に名前を付けて分ける
rows = load_rows("data.csv")
active = [row for row in rows if row["active"]]
result = [normalize(row["name"]) for row in active]
```

- インデントは 4 文字（言語の慣習が 2 文字ならそれに従う）。タブではなく空白を使う
- 長い URL や文字列は変数に入れる
- シェルのコマンドは `\` で改行する

### 1 つのコードは 20〜30 行まで

1 つのコードブロックが長いと、読者はどこが大事なのかわからなくなります。
長いプログラムは、説明する単位で分けて少しずつ示し、全体は GitHub などで配布して URL を書くのがおすすめです。
省略した部分は `# ...（省略）...` のように、コメントで省略したことがわかるようにします。

### 実行結果は分けて書く

コマンドと実行結果は、別のコードブロックにするとどこまでが入力かがはっきりします。

````markdown
保存したら、ターミナルで次のように実行します。

```bash
python3 rename.py
```

次のように表示されれば成功です。

```text
IMG_0412.jpg -> 001.jpg
IMG_0413.jpg -> 002.jpg
```
````

### 本文中のコード

ファイル名・コマンド名・関数名・設定項目などは、本文中でもインラインコード（`` `book.yaml` ``）で書くと、ふつうの言葉と区別できます。
ただし、インラインコードの中は折り返されにくいため、長い文字列は避けます。

## 5. 図・画像の入れ方

### 基本

画像は本のフォルダの `images/` に置き、段落として 1 行で書きます。キャプションを付けると「図1.1」のような番号が付きます。

```markdown
![原稿からEPUBができるまで](images/build-flow.png){#fig:flow}

[@fig:flow]のように、原稿は Pandoc で EPUB に変換されます。
```

- **段落の途中に置いた画像は図にならない**（番号もキャプションも付かない）。必ず前後に空行を入れる
- 本文では「下の図」ではなく **`@fig:ID` で参照** する。文字の大きさによって図の位置が変わるため
- 参照先の ID が見つからないと、ビルドと原稿チェックで警告が出る

### 図を作るときのコツ

| 項目 | おすすめ | 理由 |
|:--|:--|:--|
| 形式 | 図・スクリーンショットは PNG、写真は JPEG | ビルド時に Kindle 向けに最適化される（大きすぎる画像の縮小、透過の除去など） |
| 大きさ | 幅 1,200px 以上 | 高解像度の端末でもぼやけない |
| 縦横比 | 横長より **正方形〜縦長** | スマートフォンを縦に持つと、横長の図は小さく表示される |
| 色 | **白黒でも区別できる** 配色 | E-ink 端末は白黒表示。色だけで区別せず、線の種類・模様・ラベルを併用する |
| 文字 | 図の中の文字は大きめに、少なめに | 図は画面の幅に縮小される。細かい説明は本文に書く |
| 背景 | 白（透過にしない） | ダークモードで読む人もいるため。透過 PNG はビルド時に白背景に変換される |

スクリーンショットは、必要な部分だけを切り抜き、注目してほしい場所を枠で囲むとわかりやすくなります。

### 図に頼りすぎない

Kindle には、文字を音声で読み上げる機能や、文字を大きくして読む人がいます。
図だけで説明を終わらせず、**図が見えなくても本文で内容がわかる** ように書きましょう。
キャプション（`![` と `]` の間の文字）は画像の代替テキストにもなるので、「図」「画像」ではなく内容を表す言葉にします。

```markdown
✕ ![図](images/flow.png){#fig:flow}
○ ![原稿からEPUBができるまで](images/flow.png){#fig:flow}
```

## 6. 表の入れ方

```markdown
| 名前        | 用途               |
|:------------|:-------------------|
| Python 3.12 | スクリプトを動かす |
| エディタ    | スクリプトを書く   |

: 準備するもの {#tbl:tools}

必要なものは[@tbl:tools]のとおりです。
```

表の直後に `: キャプション {#tbl:ID}` を書くと「表1.1」のような番号が付きます。

- **列は 3〜4 列まで**。スマートフォンの幅に収まらない表は、セルの中で何度も折り返されて読みにくくなる
- 1 つのセルには短い語句だけを書く。文章で説明が必要なら、表の下の本文や箇条書きに書く
- 列が多い表は、**2 つの表に分ける**か、**見出しと箇条書きに書きかえる**か、画像にする
- 表の中で `|` を書くときは `\|` と書く

列が多くなりそうなときは、箇条書きのほうが読みやすいことがよくあります。

```markdown
### Python 3.12
- 用途：スクリプトを動かす
- 入手先：python.org
```

## 7. 囲み・脚注・ルビの使い分け

### 囲み（注意書き・コラム）

本文の流れから外れる情報は、`:::` で囲みます。

```markdown
::: warning
ファイル名の変更は元に戻せません。
必ずフォルダのコピーで試してください。
:::

::: {.column title="コラム：なぜ連番は 3 桁にするのか"}
`1.jpg`、`10.jpg`、`2.jpg` のように、桁数がそろっていないと名前順が崩れるためです。
:::
```

| クラス | 既定の見出し | 使いどころ |
|:--|:--|:--|
| `note` | メモ | 補足。読み飛ばしても先に進める情報 |
| `tip` | ヒント | 知っていると便利な近道 |
| `important` | 重要 | 必ず読んでほしい前提・条件 |
| `warning` | 注意 | 読者が失敗しやすい点 |
| `caution` | 警告 | データの消失など、取り返しのつかない操作 |
| `column` | コラム | 背景知識や余談 |

`title="..."` で見出しを変えられ、`title=""` で見出しなしになります。

囲みは **1 節に 1〜2 個まで** にしましょう。多すぎると、どれが大事なのかわからなくなります。
また、囲みの中に手順の続きを書くと、読み飛ばした読者がつまずくので、手順は必ず本文に書きます。

### 脚注

```markdown
途中経過を表示させておくと安心です[^print]。

[^print]: `print` は画面に文字を表示する関数です。
```

脚注は各章の末尾にまとめて出力され、Kindle では番号をタップするとポップアップで表示されます。
用語の補足や出典など、**本文の理解に必須ではない情報** に使います。読者がタップする手間がかかるので、多用は避けます。

### ルビ

```markdown
{紫陽花|あじさい}         グループルビ（熟語全体に読みを付ける）
{東京|とう|きょう}        モノルビ（1 文字ずつ読みを付ける）
[憂鬱]{ruby="ゆううつ"}   span 記法（表の中ではこちらを使う）
```

難読語や、読者が読み方に迷う専門用語の **初出だけ** に付けます。

## 8. 縦書きで気をつける点

縦書き（`layout.writing_mode: vertical`）では、和文は縦に、英単語は横倒しに組まれます。
コードや表はそのまま縦にすると読めないため、既定では **横組みを 90 度回した向き** で表示されます（端末を右に傾けると横書きとして読めます）。
この表示方式は `layout.vertical.code_blocks` / `tables` で変えられます（詳しくは [README の「縦書きの表示の工夫」](../README.md#縦書きの表示の工夫)）。

### 数字の書き方

縦書きでは、数字の書き方で読みやすさが大きく変わります。

| 書き方 | 縦書きでの表示 | 使いどころ |
|:--|:--|:--|
| 漢数字（`三つ`、`十年`） | 縦に並ぶ | 和語・慣用句・概数（「一つずつ」「数十個」） |
| 2 桁までの算用数字（`12`） | 自動で **縦中横**（横に並べて 1 文字分に収める） | 日付・個数・章番号 |
| 3 桁以上の算用数字（`2026`） | 横倒し | バージョン番号・型番・年号。漢数字（`二〇二六`）にする方法もある |

本の中で数字の書き方をそろえておくと、読者が迷いません。
たとえば「数量・日付は算用数字、慣用的な表現は漢数字」のように決めておきます。
縦書きのサンプル（`books/vertical-sample/textlint.json`）では、漢数字と算用数字の使い分けを書き手が決められるよう、それに関する原稿チェックのルールを外しています。

自動で縦中横にならない箇所や、向きを変えたい箇所は、手動で指定します。

```markdown
[100]{.tcy}円         3 桁を縦中横にする（3 桁以上は詰まって読みにくくなるので注意）
[AI]{.upright}の活用   英字を 1 文字ずつ正立させる（2〜3 文字の略語に）
[No.1]{.sideways}     横倒しにする
```

### 英単語・記号

- **短い略語（AI、PC、OS）** は、横倒しのままか `{.upright}` で正立させるか、本の中で統一する
- **長い英単語・英文** はなるべく減らし、カタカナや日本語に言いかえる。どうしても必要なら横倒しのままにする
- 括弧やダッシュ、三点リーダー（`……`）は全角で書く。半角の `()` や `-` は縦書きで向きが崩れることがある
- 感嘆符・疑問符は全角（`！` `？`）で書く。`!!` `!?` は自動で縦中横になる

### コードと表は少なめに、短く

縦書きの本でも、コードや表は書けます。ただし、読者は端末を傾けて読むことになるため、次の点に気をつけます。

- **1 章あたりのコード・表の数を減らす**。コードが中心の本なら横書きを選ぶ
- コードブロックの前に「端末を右に傾けると読めます」と一度案内しておくと親切（サンプルの `books/vertical-sample/chapters/02-first-script.md` を参照）
- 表は、和文中心で短いものなら `tables: vertical`（縦組みのまま）にすると傾けずに読める

```yaml
layout:
  writing_mode: vertical
  vertical:
    code_blocks: sideways   # sideways（既定）/ horizontal / vertical
    tables: vertical        # 和文中心の小さな表だけなら
```

### 方向を表す言葉

縦書きでは、横書きの「上下左右」が入れ替わります。「左の図」「右の列」などの言葉は避け、番号で参照しましょう。
同じ原稿を横書きと縦書きの両方で出す可能性があるなら、なおさら方向を表す言葉は使わないのが安全です。

## 9. 書き終えたら確認すること

### 原稿チェック

```bash
npm run lint -- books/my-book
```

表記ゆれ、文の長さ、参照先の ID、画像の有無、リンク切れをまとめて確認できます。
自動で直せる指摘（表記の統一など）は、次のコマンドで原稿に反映できます。

```bash
npm run lint:fix
```

### ビルドして実機に近い表示で読む

```bash
make book BOOK=books/my-book
```

ビルドした EPUB を Kindle Previewer で開き、少なくとも次の 3 つの表示で読み通します（詳しくは [README の「Kindle Previewer での確認方法」](../README.md#kindle-previewer-での確認方法)）。

- **スマートフォン**（縦長・小さい画面）… 表が収まるか、図の文字が読めるか
- **E-ink 端末**（白黒）… 図の色分けやハイライトが区別できるか
- **タブレット**… 1 段落が長すぎて読みにくくないか

### 最後に声に出して読む

書き上げた章を、声に出して（または読み上げ機能で）読んでみましょう。
息継ぎに困る文は長すぎる文です。指示語の指す先がすぐにわからない箇所も、耳で聞くと見つけやすくなります。

| やりたいこと | 書き方 |
|:--|:--|
| 番号付きの章 | `# 章タイトル {#sec:ID}` |
| 番号なしの章 | `# はじめに {.unnumbered}` |
| 付録 | `# 付録の章 {.appendix}` |
| 節・項 | `## 節` / `### 項` |
| 太字・斜体・コード | `**太字**` / `*斜体*` / `` `code` `` |
| リンク | `[文字](https://example.com)` |
| コード（番号付き） | ```` ```{.python #lst:ID caption="キャプション"} ```` |
| 図（番号付き） | `![キャプション](images/foo.png){#fig:ID}` |
| 表のキャプション | 表の直後に `: キャプション {#tbl:ID}` |
| 相互参照 | `@sec:ID` / `@fig:ID` / `@tbl:ID` / `@lst:ID`（`[@fig:ID]` も可） |
| 囲み | `::: note` 〜 `:::`（note / tip / important / warning / caution / column） |
| 囲みの見出しを変える | `::: {.column title="コラム：見出し"}` |
| 脚注 | `本文[^名前]` と `[^名前]: 内容` |
| ルビ | `{漢字\|かんじ}` / `{東京\|とう\|きょう}` / `[漢字]{ruby="かんじ"}` |
| 縦中横・正立・横倒し（縦書き） | `[12]{.tcy}` / `[AI]{.upright}` / `[ABC]{.sideways}` |
| 改ページ | `::: pagebreak` 〜 `:::` |
| 中央揃え・右（下）揃え | `::: center` 〜 `:::` / `::: right` 〜 `:::` |
